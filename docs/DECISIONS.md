# Decisions

One line per decision with the reason. IDs are stable; add new ones at the end of their section. Where a decision deviates from `docs/BRIEF.md`, it says **(deviates from brief)**.

## Toolchain and versions (verified 2026-11-16)

- **D-001 npm** as package manager. Reason: Expo default, lockfile caches cleanly in CI, no hoisting config needed for React Native.
- **D-002 Expo SDK 58 / React Native 0.88.1 / React 19.3.0.** Reason: newest stable Expo SDK (`npm view expo dist-tags`: `latest` = 58.0.x) and the Kotlin compile gate passes on it with the chosen WebRTC package (see Evidence E-3). Fallbacks if a device test regresses: SDK 57 = RN 0.86.3, SDK 56 = RN 0.85.3, SDK 55 = RN 0.83.10.
- **D-003 TypeScript pinned to `~6.0.3`.** Reason: Expo SDK 58's template pins it; `typescript@latest` is 7.0.2 (native compiler) but `typescript-eslint` supports `<6.1.0` and `ts-jest` `<7`. Revisit when the tooling supports TS 7.
- **D-004 WebRTC package: `@livekit/react-native-webrtc` 150.1.1, exact pin.** Reason: the brief prefers it; stage 2's `@livekit/react-native@3.1.0` peers on `^150.1.0`, so one WebRTC build serves both stages; it compiles on RN 0.88.1; actively released (150.1.1 on 2026-10-26). See Evidence E-1..E-3.
- **D-005 MMKV kept, with `react-native-nitro-modules` pinned to exactly `0.35.9`.** Reason: user's default; `react-native-mmkv@4.3.2` was generated against Nitro 0.35.9 while `latest` is 0.37.2 (Nitro is pre-1.0, minor versions can break generated code) and the compile gate passes with 0.35.9. MMKV 4 ships a web fallback, so the web target needs no stand-in.
- **D-006 `@playwright/test` pinned to exactly `1.63.0`.** Reason: matches the Chromium preinstalled in the cloud image (`/opt/pw-browsers/chromium-1243`); the Playwright download hosts (`cdn.playwright.dev`, `playwright.download.prss.microsoft.com`) are blocked by the session allowlist.
- **D-007 ESLint 9.x with `eslint-config-expo` flat config.** Reason: matches `eslint-config-expo@58`; ESLint 10 resolves in a dry run but has not been proven with the Expo plugin set. Revisit (npm marks 9.39.5 as no longer supported).
- **D-008 `@livekit/react-native-expo-plugin` not used in stage 1.** Reason: it exists for the LiveKit RN SDK (stage 2); the WebRTC fork autolinks without it.
- **D-009 `expo-dev-client` not included in the test APK.** Reason: its launcher screen would block an offline start in a pocket. The debug variant embeds the JS bundle so the CI APK runs without Metro (`react { debuggableVariants = [] }` through a config plugin). Local development uses `expo run:android` + Metro.
- **D-010 Android SDK levels: compileSdk 37, targetSdk 36, build-tools 37.0.0, NDK 27.1.12297006 (React Native 0.88 / Expo SDK 58 defaults), minSdk 29 (ours).** Reason: every Expo SDK 58 library requires compileSdk >= 37 (an earlier compileSdk 36 override failed `:app:checkDebugAarMetadata`); targetSdk 36 is what the platform ships and tests. Raising targetSdk to 37 (Android 17) changes runtime behaviour and needs the behaviour-change review plus device testing, so it is a deliberate later step (one constant in `app.config.ts`). **(deviates from brief: 'target the latest stable SDK')**

## Architecture

- **D-011 Native modules are local Expo modules in `modules/`, not TurboModules inside `android/`. (deviates from brief)** Reason: the brief allows "local Expo modules if they fit better"; `expo prebuild --clean` regenerates `android/` and would delete app-local Kotlin, local modules autolink and merge their own manifest (service, permissions). `android/` is still generated and committed. `specs/` holds the TypeScript description of each module's JS surface.
- **D-012 Identity in `config/identity.json` (JSON, not TS).** Reason: `app.config.ts` is loaded by Node via Expo's config loader, which cannot resolve an extensionless `.ts` import; JSON loads in Node, Metro, Jest and Gradle alike. Holds display name, application id, URL scheme, pairing prefix, NSD service type, Wi-Fi Direct name prefix, notification channel id.
- **D-013 Placeholder application ID `app.pillion.intercom`.** Reason: any reverse-DNS placeholder; rename in `config/identity.json` (uninstall + re-pair test phones afterwards).
- **D-014 Ownership gaps in the brief's table filled.** `src/platform/link` + `src/platform/service` native wrappers -> `android-native`; `src/platform/media` + `audio` -> `media`; `src/platform/permissions` + `storage` -> `ui`; every `*.web.ts` -> `web-verify`. Reason: the table lists no owner for them and one-owner-per-directory is what makes parallel work safe.
- **D-015 Two extra platform ports: `permissions/` and `storage/`.** Reason: onboarding needs a permission port and the pairing store needs Keystore-backed storage; both must have web fakes like every other interface.
- **D-016 Platform interface files stay in `src/platform` (as in the brief) and `src/core` may import exactly those, type-only.** Reason: follows the brief's layout; the allowlist is enforced by ESLint zones so nothing else leaks into core.
- **D-017 `MediaEngine` (whole ride) + `MediaSession` (one per negotiation attempt).** Reason: a reconnect must not re-acquire the microphone; the loopback self-test is just two sessions with `sendLocalAudio: false` on the receiver.
- **D-018 Link is a byte pipe; framing, auth and JSON live in TypeScript (`src/core/protocol`).** Reason: unit-testable on Node, identical on Android, web relay and the in-memory fakes; native code stays thin.
- **D-019 Handshake: mutual HMAC proofs of the 32-byte secret, HKDF direction keys, implicit message counters, MAC on every frame including SDP.** Reason: proves possession before any session message is accepted; replay, reorder, drop and tamper all fail the MAC; MAC'd SDP binds the DTLS fingerprint to the pairing. Details in `src/core/protocol/messages.ts`.
- **D-020 Audio cues play through the native `AudioRoute` (`USAGE_VOICE_COMMUNICATION`), not a media-player library.** Reason: cues must come out of the communication device the call uses; a music-stream player may route to the speaker while in communication mode.
- **D-021 Jest runs in a plain Node environment (babel-preset-expo transform, `@noble` transpiled); no component tests.** Reason: a stray react-native import in `src/core` must fail its tests; UI is verified through the web build + Playwright screenshots, which is what the brief asks for.
- **D-022 Developer features are gated by a runtime developer-mode switch (7 taps on the version label), not by `__DEV__`.** Reason: the test APK must carry the "paste pairing string" path, the earpiece/speaker override and the tunables screen, but those must stay hidden from ordinary use.
- **D-023 Product-name-bearing labels inside crypto KDF strings (`pillion/v1/...`) are protocol identifiers, not display names.** Reason: they must stay stable across a rename; changing them is a protocol break (bump `PROTOCOL_VERSION`).
- **D-026 Platform extension at the factory-module level.** Each `src/platform/<area>` has the interface file, `create<X>.ts` (native), `create<X>.web.ts` (web twin, same export name) and a shared `index.ts`. Reason: an `index.web.ts` would shadow the whole area on web; twins let Metro pick per module and keep the barrel shared, and a type-level parity test compares native and web signatures.
- **D-027 Subagents run as general-purpose agents in the first session.** `.claude/agents/*.md` are the durable definitions (picked up by later sessions); this session started before `.claude/agents/` existed, so the harness did not load them. Each delegation told the agent to read its role file first and follow it. Reason: keeps the roles reusable without a restart.
- **D-028 Native modules: directory `modules/intercom-native`, Kotlin package `expo.modules.intercom`, JS module names `IntercomLink`, `IntercomAudioRoute`, `IntercomRideService`.** Reason: Expo module names are global per app, so product-neutral prefixed names avoid collisions and survive a rename of the product.
- **D-045 Android manifest least privilege: `android.blockedPermissions` removes `SYSTEM_ALERT_WINDOW` and `READ/WRITE_EXTERNAL_STORAGE` from the merged manifest, `android.allowBackup: false`, and no `scheme` in `app.config.ts` (so no BROWSABLE deep-link intent filter).** Reason: the app uses none of those permissions (no shared storage, no audio stored; the overlay is only the RN dev menu, which the debug-only manifest may still request); pairing records must not go to cloud backup (expo-secure-store's data extraction rules stay, since `allowBackup=false` does not stop Android 12+ device-to-device transfer and they exclude the SecureStore prefs); a registered scheme lets any web page launch the app into any route and nothing on Android uses it yet (`config/identity.json` keeps `urlScheme` for the navigation prefixes; re-add `scheme` when a real deep link exists).
- **D-046 `IntercomLink.isWifiConnected` checks every network (`ConnectivityManager.allNetworks`), not only `activeNetwork`; `specs/IntercomLink.ts` comment updated to match.** Reason: Android does not make a Wi-Fi network without internet (router-only LAN, partner's hotspot: the core use case) the default network while mobile data is up, so `activeNetwork` alone reports "not connected" there. `listInterfaces` skips an interface whose reads throw `SocketException` (it vanished mid-listing) instead of failing the whole call.

- **D-046 Pairing service in `src/app/pairing.ts`; the host saves its record when the plate is first shown and reuses that unused offer (host record with `partnerName === null`) until "New code" replaces it.** Reason: the QR is one-way, so the host can never know whether a code was scanned; generating a new secret on every open would silently break a guest who already scanned. "New code" saves the new offer before removing the old one, so a failure never leaves the host without a code.
- **D-047 Native randomness is expo-crypto `getRandomValues`, not `getRandomBytes`.** Reason: expo-crypto 58 `getRandomBytes` falls back to `Math.random` in `__DEV__` when `global.nativeCallSyncHook` is missing, and bridgeless New Architecture never installs that hook (only `JSIExecutor` does), so a debug APK would have generated pairing secrets from Math.random. Twin: `src/platform/crypto/createRandomBytesSource{,.web}.ts`, parity-checked.
- **D-048 expo-camera plugin with `recordAudioAndroid: false`, `RECORD_AUDIO` declared explicitly in `android.permissions`.** Reason: the camera only scans; the microphone permission had only been in the manifest as a side effect of expo-camera's default. The merged manifest is unchanged from M0 (same four kept permissions).
- **D-049 Camera scanner is a feature twin (`src/features/pair/QrScanner{,.web}.tsx`); on web the paste field is shown without developer mode.** Reason: the web build has no camera scanning and must still prove the pairing flow end to end; native shows the paste field only in developer mode.
- **D-050 expo-clipboard (~58.0.4, the SDK 58 version) for the developer-only "Copy pairing string", with Android `isSensitive`.** Reason: React Native has no clipboard; the copy is needed for the web e2e and the device export-secret check. Sensitive flag hides the Android 13+ clipboard preview; the pasted string is masked (`secureTextEntry`) on the guest.
- **D-051 Home shows the most recent pairing; the list stays a list.** Reason: a phone can hold a host offer and a guest pairing at once; the newest is the one the user just made.
- **D-052 The `?camera=denied` web preview toggle (D-037) is removed.** Reason: the denied state is now real (expo-camera permission) and native only; the web twin has no camera.

## Cloud environment

- **D-024 Gradle in cloud sessions uses Google's Maven Central mirror (`maven-central.storage-download.googleapis.com`) through `~/.gradle/init.d/00-central-mirror.gradle`.** Reason: Maven Central now sits behind Cloudflare and answers about 25% of parallel requests with HTTP 429 (no `Retry-After`) from the shared egress IP; Gradle gives up after three quick retries. The mirror returned 200 for 40/40 parallel requests. The init script lives in the user's Gradle home and is written by `scripts/cloud-setup.sh`; the repo's Gradle files and CI use real Central.
- **D-025 `scripts/fetch-doc.sh` for subagents.** Reason: background subagents may not get WebFetch; the script prints a page as text through the session proxy.
- **D-029 CI = three jobs (checks, web-e2e, android), actions on current majors (checkout v7, setup-node v7, setup-java v6, cache v6, upload-artifact v7; tags verified with `git ls-remote`).** Reason: majors keep moving, a pinned-and-verified list avoids a broken first run; no SHA pinning because the repo is private and has no secrets or write permissions (`permissions: contents: read`).
- **D-030 `scripts/cloud-setup.sh` is self-contained, always exits 0, uses `timeout` on every download and only installs what is missing.** Reason: it is pasted into the environment's setup field and runs from the directory above the repo; a failing setup script would block the session. Tested 2026-11-17: clean install 24 s, re-run under 1 s. sdkmanager has no metrics flag (`sdkmanager --help`), so there is no opt-out to pass.
- **D-031 ESLint stays on 9.x.** Reason: trialled eslint@10.15.0 with eslint-config-expo 58.0.4: `eslint-plugin-react` 7.37.5 crashes (`contextOrFilename.getFilename is not a function`) and its latest peer range is `<=9.x`, same for `eslint-plugin-import`. Retry when those publish eslint 10 support.
- **D-032 `tsconfig.json` sets `"types": ["jest", "node"]` and `babel-preset-expo` becomes a direct devDependency.** Reason: TypeScript 6 no longer auto-includes `@types/*` (test files lost `describe`/`it`), and `npm ci` nests `babel-preset-expo` under `expo/node_modules` so `babel-jest` cannot resolve it from the repo root (all Jest suites failed in a clean install).

## UI design ("Brass Chronograph", 2026-11-17)

- **D-033 Visual language "Brass Chronograph": warm near-black (#0B0A08, no pure black), ivory text, brass accent, patina/amber/vermilion status, oxblood End ride; chamfered SVG plates instead of rounded rectangles; hairline-ruled lists instead of boxed cards.** Reason: the product owner rejected the generic dark/neon look; an instrument dial reads well at night and in glare, and every state still shows ring + icon + word. Contrast pairs are asserted in `src/app/theme.test.ts`.
- **D-034 Fonts: Marcellus, Marcellus SC, Barlow Semi Condensed (400/500/600), Cormorant Garamond 500 Italic via `@expo-google-fonts/*` 0.4.1 (MIT AND OFL-1.1) and `expo-font` `useFonts`, imported per weight from the package subpaths.** Reason: bundled offline (only six .ttf files reach the bundle), no network; the in-app splash waits for fonts or the hydration timeout, and a load error falls back to the system font without blocking. The `expo-font` config plugin is not used (runtime loading is enough).
- **D-035 Motion uses the React Native Animated API, not Reanimated.** Opacity/transform run on the native driver; SVG `strokeDashoffset` (gauge arc, hold-to-end trace) uses `Animated.createAnimatedComponent(Path)` on the JS driver, only for one-shot animations of 900 ms or less (plus the rate-limited gauge pointer). Reason: no worklets/Babel setup risk at this scale; verified working on react-native-web. `useAnimatedValue` is a local hook because react-native-web does not export React Native's.
- **D-036 Reduced motion: `useReducedMotion` reads `AccessibilityInfo.isReduceMotionEnabled` + `reduceMotionChanged`, and on web also `prefers-reduced-motion`.** Then values jump and transitions are 120 ms crossfades; loops (lamp breath, spinner, stopwatch) also stop whenever `AppState` is not active. Haptics (`expo-haptics`) and audio cues stay on.
- **D-037 M0 verification toggles on web: `?preview=connecting|reconnecting|headset-missing` (ride sample state, also chosen on the debug screen), `?camera=denied`, `?fontScale=1.3` (emulates the system font scale with the per-variant caps, since react-native-web ignores it).** Reason: the live session arrives in M1; the screens must be screenshot in every state now. All live in `src/app/preview.ts` and go away with the placeholders.
- **D-038 Hold-to-end (1.0 s) for End ride, with an accessibility `activate` action that asks for a second activation instead of the hold.** Reason: an accidental pocket or glove tap must not hang up both phones, and screen-reader users must not need a timed gesture.

- **D-039 Ride-gauge geometry is a pure function (`gaugeLayout` in `src/features/components/Dial/geometry.ts`): the sub-dials sit fully inside the circle the pointer never enters, 6 dp clear of the arc band and the pointer at every value, for gauges 296-340 dp (phones 340 dp wide and up).** Reason: a review found the pointer landing on the battery sub-dial; `geometry.test.ts` now checks the clearance across the whole sweep.
- **D-040 Sub-dial and dial legends get their tracking fitted to the chord they sit on (`fitTracking`, 0.66 em per Marcellus SC capital, measured 0.50-0.64 in Chromium); a word that cannot fit untracked is shortened ("BATT").** Reason: no text measurement in SVG on native; a conservative estimate plus a unit test keeps legends off the rims.
- **D-041 The not-paired hero dial no longer repeats the night-road etching inside its face; RIDER / PILLION are engraved under the "?" sub-dials and the top text arc is omitted on the compact dial.** Reason: the full etching sits directly above it on the same screen, and inside the 240 dp dial it only crossed the sub-dials as stray lines (review finding).
- **D-042 The ride caption under "with <partner>" is derived from the session state (`rideCaption` in `sessionStatus.ts`); unknown values show an em dash with no unit.** Reason: "Voice clear" while connecting or reconnecting was a false status on the safety-relevant screen.
- **D-043 Hold-to-end logic lives in a pure `holdController.ts` (Node unit tests), not in the component.** Reason: the project has no React Native component renderer in Jest (UI is verified through web + Playwright); the controller stops in-flight holds on unmount, disarms the screen-reader confirm after 5 s and resets the stroke after completion.
- **D-044 The End ride gradient is deepened to #832B20 -> #651E16 (ivory >= 7.4:1), never lighter than the spec's `oxblood` #8B2A1D.** Reason: the brighter #9A3123 top read as an alarm button and pulled the eye off the gauge.

## Evidence

- **E-1 Candidates (npm metadata, 2026-11-16).** `@livekit/react-native-webrtc` 150.1.1 (6 releases since 2026-06, native lib `io.github.webrtc-sdk:android-prefixed:150.7871.04`, package prefix `livekit.org.webrtc`); `react-native-webrtc` 155.0.1 (upstream; Android lib `org.jitsi:webrtc:155.+`, a different build, not what LiveKit uses); `@stream-io/react-native-webrtc` 145.4.2 (Android lib `io.getstream:stream-video-webrtc-android:145.17.0`, Kotlin parts). All three declare only `react-native >=0.60` (or `>=0.73`) as peer: that range proves nothing, so compatibility was established by source inspection and a real build (E-3).
- **E-2 New Architecture status.** None of the three has a `codegenConfig` or TurboModule spec: each is a legacy-style Java `ReactContextBaseJavaModule` (`com.oney.WebRTCModule`) running through React Native's interop layer, as the brief warned. All three expose `WebRTCModuleOptions` with a `fieldTrials` string (passed to `PeerConnectionFactory.InitializationOptions.setFieldTrials`) and an injectable `audioDeviceModule`: the hooks for risk 1 and for hardware AEC/NS control. **Correction (media evidence, docs/evidence/media-webrtc-package.md): there is NO `WebRTC-IncludeWifiDirect` field trial in this libwebrtc build; the switch is the static `NetworkMonitorAutoDetect.setIncludeWifiDirect(boolean)`, and the relevant trial is `WebRTC-AndroidNetworkMonitor-IsAdapterAvailable/Disabled/`. Both must be set in `Application.onCreate`. The brief's risk 1 wording was partly wrong.** **Runtime behaviour of the interop layer on a device is untested**; only the build is proven.
- **E-3 Build gate.** Expo SDK 58.0.25 (RN 0.88.1, Kotlin 2.2.10, AGP 9, Gradle 9.4.1, JDK 21, NDK 27.1.12297006, compileSdk 37 (first attempt with a 36 override failed assemble), minSdk 29): `./gradlew :app:compileDebugKotlin` -> `BUILD SUCCESSFUL in 1m 57s`, with `:livekit_react-native-webrtc:compileDebugJavaWithJavac`, `:react-native-mmkv:compileDebugKotlin` and `:react-native-nitro-modules:compileDebugKotlin` executed, zero compiler warnings. `./gradlew :app:assembleDebug -PreactNativeArchitectures=arm64-v8a` -> `BUILD SUCCESSFUL in 2m 13s`, 112 MB `app-debug.apk` (includes the NDK/CMake build of the New Architecture app, Nitro/MMKV and libwebrtc). Note `compileDebugKotlin` alone is NOT a sufficient gate: `:app:checkDebugAarMetadata` (compileSdk requirements) only runs in assemble, so CI's assemble job matters.
- **E-4 Stage-2 compatibility.** `npm view @livekit/react-native@3.1.0 peerDependencies` -> `@livekit/react-native-webrtc: ^150.1.0`, `livekit-client: ^2.20.0`.

## Findings: things in the brief that were wrong, outdated or needed adjusting

- Maven Central rate-limits the cloud egress (HTTP 429), so "Google's SDK and Maven downloads may be blocked" was not the actual problem; SDK, Google Maven, Gradle and npm hosts were all reachable (D-024).
- The newest Expo SDK is 58 (RN 0.88), far past what the brief assumed; TypeScript 7 exists but the tooling does not support it yet (D-003).
- `react-native-mmkv` v4 is a Nitro module and needs a pinned `react-native-nitro-modules` (D-005).
- A "debug APK" does not run offline by default (JS comes from Metro) and `expo-dev-client` adds a launcher: the CI APK must embed the bundle (D-009).
- The brief's directory table has no owner for several `src/platform` folders (D-014) and its file tree puts Kotlin in `android/`, which `expo prebuild --clean` would delete (D-011).
- `NetworkMonitorAutoDetect.setIncludeWifiDirect` / `IncludeWifiDirect` (risk 1): status is recorded in `docs/evidence/media-*.md` once the `media` subagent has inspected the AAR.
