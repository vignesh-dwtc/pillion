# android-native: M1/M2 research note

Written 2026-11-17 for milestone M1 (LAN link, audio route, ride service) and M2 (Wi-Fi Direct). Every statement marked **[doc]** was read on developer.android.com in this session (URL given); **[ours]** is a design consequence for this app; **[unverified]** was not confirmed against a page and must be checked before relying on it. Nothing here was run on a device.

App facts: minSdk 29, targetSdk 36, compileSdk 37 (DECISIONS D-010). The service is started from a user tap, needs the microphone (WebRTC capture keeps running with the screen off) and a link to another device (connectedDevice).

## 1. Foreground service: microphone + connectedDevice, API 29 to 36

Sources: https://developer.android.com/develop/background-work/services/fgs/service-types, https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start, https://developer.android.com/develop/background-work/services/fgs/declare, https://developer.android.com/develop/background-work/services/fgs/timeout, https://developer.android.com/about/versions/15/behavior-changes-15, https://developer.android.com/reference/android/Manifest.permission

### Manifest entries (module manifest, merged into the app)

```xml
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_MICROPHONE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_CONNECTED_DEVICE" />
<uses-permission android:name="android.permission.RECORD_AUDIO" />
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
<uses-permission android:name="android.permission.CHANGE_WIFI_MULTICAST_STATE" />
<uses-permission android:name="android.permission.CHANGE_NETWORK_STATE" />
<uses-permission android:name="android.permission.ACCESS_NETWORK_STATE" />
<uses-permission android:name="android.permission.WAKE_LOCK" />
<service android:name=".RideForegroundService" android:exported="false"
         android:foregroundServiceType="microphone|connectedDevice" />
```

- `FOREGROUND_SERVICE_MICROPHONE` and `FOREGROUND_SERVICE_CONNECTED_DEVICE` exist since API 34, protection level normal (granted at install, no prompt) **[doc]** (Manifest.permission: "Added in API level 34", "normal|instant"). On API 29-33 the unknown permissions are simply ignored; `FOREGROUND_SERVICE` itself (API 28, normal) is what API 29-33 needs, and the `foregroundServiceType` attribute exists since API 29, so one manifest serves all levels. **[ours]**
- Service types are mandatory from Android 14 (API 34) for apps targeting 34+: "Beginning with Android 14 (API level 34), you must declare an appropriate service type for each foreground service ... and request the appropriate foreground service permission for that type" **[doc]**. A missing declaration makes `startForeground()` throw `MissingForegroundServiceTypeException` **[doc]** (fgs/declare).
- `connectedDevice` has a runtime prerequisite: at least one of the manifest permissions `CHANGE_NETWORK_STATE`, `CHANGE_WIFI_STATE`, `CHANGE_WIFI_MULTICAST_STATE`, `NFC`, `TRANSMIT_IR`, or a granted runtime permission `BLUETOOTH_CONNECT/ADVERTISE/SCAN`, `UWB_RANGING`, or a UsbManager permission **[doc]**. Declaring `CHANGE_WIFI_MULTICAST_STATE` (we need it for the multicast lock anyway) satisfies it with no prompt. **[ours]**
- `microphone` has the runtime prerequisite `RECORD_AUDIO` granted **[doc]**.
- Call `startForeground(id, notification, ServiceInfo.FOREGROUND_SERVICE_TYPE_MICROPHONE or ServiceInfo.FOREGROUND_SERVICE_TYPE_CONNECTED_DEVICE)` on API 29+ (the 3-argument overload exists since API 29). **[ours]** Types passed in code must be a subset of the manifest declaration. **[unverified: standard behaviour, not re-read this session]**

### Runtime prerequisites and what fails

| Android  | Behaviour **[doc]** unless noted                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 29 to 30 | A foreground service needs `FOREGROUND_SERVICE` and a notification. No type enforcement. A background start of a microphone service is allowed but the service has no microphone access while the app is in the background **[doc]**: "the system would let you create the service, but the service wouldn't have access to the needed resources".                                                                                                                                                                       |
| 31 to 33 | Background start of any foreground service throws `ForegroundServiceStartNotAllowedException` unless an exemption applies (restrictions-bg-start). Microphone while-in-use semantics as above.                                                                                                                                                                                                                                                                                                                           |
| 34 (14)  | Type + type permission mandatory. At creation the OS checks the type's prerequisites: a microphone service without `RECORD_AUDIO` throws `SecurityException`; and since `RECORD_AUDIO` is a while-in-use permission, creating a microphone service while the app is in the background also throws `SecurityException` ("the system sees that your app doesn't currently have the required permissions") **[doc]**. `checkSelfPermission` returns GRANTED in the background anyway and does not protect you **[doc]**.    |
| 35 (15)  | Same rules. New: `dataSync` and `mediaProcessing` types get a 6 h / 24 h timeout with `onTimeout` **[doc]**; microphone and connectedDevice have NO timeout: the timeout page says the restriction "currently only applies to dataSync and mediaProcessing" **[doc]**. BOOT_COMPLETED receivers cannot launch microphone, mediaPlayback, dataSync, mediaProjection or phoneCall services **[doc]** (irrelevant: we never start from boot). `SYSTEM_ALERT_WINDOW` exemption now needs a visible overlay window **[doc]**. |
| 36 (16)  | No change to these types found in the 16 all-apps behaviour page (only JobScheduler quota interplay with a running FGS). **[doc, negative result: grep of the page]**                                                                                                                                                                                                                                                                                                                                                    |
| 37 (17)  | See section 7.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |

Starting from a user tap is what makes this work: "Your app transitions from a user-visible state, such as an activity" and "The user performs an action on a UI element related to your app ... notification, widget, or activity" are exemptions to the background start rule, and the while-in-use rule requires `startForegroundService()` to be called "while your app has a visible activity, unless the service falls into one of the defined exemptions" (a service started by interacting with a notification is an exemption) **[doc]**. Consequences for the design **[ours]**:

1. `RideService.start()` must run in the JS handler of a button press while the activity is resumed; do not start it from a push, a timer, `BOOT_COMPLETED`, or after the app was backgrounded.
2. Ask for `RECORD_AUDIO` and (API 33+) `POST_NOTIFICATIONS` before start. If notifications are denied the foreground service still runs and is exempt from the notification-permission check on most versions, but the ride is then invisible to the rider; treat denial as a warning. **[unverified: behaviour of denied POST_NOTIFICATIONS with FGS]**
3. Reconnect after a link drop happens inside the already running service, never by starting a new microphone service from the background.
4. Logcat tell-tale for a service that lost microphone access: "Foreground service started from background can not have location/camera/microphone access" **[doc]**.
5. If the user swipes the app away, a sticky service may be restarted by the system from the background; on API 34+ that restart cannot hold the microphone. Plan: the service stops itself when it was restarted without a live session (M1 decision).

## 2. NsdManager (LAN link, M1)

Sources: https://developer.android.com/develop/connectivity/wifi/use-nsd, https://developer.android.com/reference/android/net/nsd/NsdManager

Flow **[doc]**:

- Register: `NsdServiceInfo` with `serviceName`, `serviceType` ("_x._tcp", no leading/trailing garbage), `port` (use `ServerSocket(0)` and its local port, never a fixed one); `registerService(info, PROTOCOL_DNS_SD, RegistrationListener)`. Asynchronous: the name actually used arrives in `onServiceRegistered`; on a conflict Android renames to "Name (1)" / "(2)". Our parser tolerates the suffix (`NsdServiceNames.parsePairId`).
- Discover: `discoverServices(type, PROTOCOL_DNS_SD, DiscoveryListener)`; `onServiceFound` gives name + type only (the type comes back with a trailing dot, normalised by `NsdServiceNames.normalizeServiceType`); you must resolve to get host and port. Discovery is expensive, stop it when not needed.
- Resolve (legacy): `resolveService(info, ResolveListener)`. One resolve at a time per listener, parallel attempts fail with `FAILURE_ALREADY_ACTIVE` (constant exists since API 16; the docs list `FAILURE_ALREADY_ACTIVE` and `FAILURE_MAX_LIMIT`). Queue resolves.

Deprecations and replacements **[doc]**:

- `resolveService(...)` (both overloads): "deprecated in API level 34 ... the returned ServiceInfo may get stale at any time after resolution ... Prefer using registerServiceInfoCallback". Replacement `registerServiceInfoCallback(NsdServiceInfo, Executor, ServiceInfoCallback)` was added in API 34 and gives continuous `onServiceUpdated` (address changes, multiple host addresses via `getHostAddresses()`), `onServiceLost`; unregister with `unregisterServiceInfoCallback`. `stopServiceResolution` ends a legacy resolve.
- Newer still, via SDK extensions (the reference says to check extension levels, not API levels): `registerServiceInfoCallback(DiscoveryRequest, Executor, ServiceInfoCallback)` "combines discovery and resolution into a single operation", available from T extensions 22 "which covers all Android 14+ devices"; `registerService(AdvertisingRequest, Executor, RegistrationListener)`. The NsdManager docs recommend these for new code.
- Decision for M1 **[ours]**: write the Kotlin behind a small interface (`ServiceDiscovery`) with two implementations: API >= 34 `registerServiceInfoCallback(NsdServiceInfo...)` after `discoverServices` (non-deprecated, stable on every Android 14+ device, compiles with compileSdk 37 without deprecation warnings), API 29-33 legacy `resolveService` with a resolve queue (`@Suppress("DEPRECATION")`, documented). The `DiscoveryRequest` overloads are not used until their extension-level availability is checked on target devices. NSD also matches the "has multiple host addresses" case: pick the address with `AdvertiseAddressSelector.bestAddress`.
- Registration must be torn down on stop (`unregisterService`), the discovery on `onServiceFound` success or timeout.

### Multicast lock

**[doc]** (NsdManager reference, "Wi-Fi Multicast Lock"): "Before T extensions 7 (Android 12 and below, and Android 13 devices without that update): Apps must manually acquire a WifiManager.MulticastLock to receive mDNS packets, even when the app is in the foreground. Starting from T extensions 7: the system automatically manages multicast reception for apps in the foreground. Background apps should still avoid taking the lock unless absolutely necessary." Our ride runs with the screen off (a background app) and API 29-33 devices exist, so: acquire a `MulticastLock` (permission `CHANGE_WIFI_MULTICAST_STATE`, normal) while advertising or discovering, plus a `WifiLock(WIFI_MODE_FULL_LOW_LATENCY)` (API 29+) during the ride so the radio does not sleep with the screen off. **[ours]** Release both in `stop`. `WIFI_MODE_FULL_LOW_LATENCY` only has effect while the app is in the foreground or runs a foreground service, which the ride does. **[unverified: the "foreground" condition of low-latency mode]**

## 3. Audio routing

Sources: https://developer.android.com/reference/android/media/AudioManager (read in full text), https://developer.android.com/develop/connectivity/bluetooth/bt-permissions, https://developer.android.com/reference/android/Manifest.permission

- `setCommunicationDevice(AudioDeviceInfo)`: **added in API 31** **[doc]**. Selects "the audio device that should be used for communication use cases, for instance voice or video calls". The device must come from `getAvailableCommunicationDevices()`, only sink (output) devices can be passed, "the matching source device is selected automatically", "The selection is active as long as the requesting application process lives, until clearCommunicationDevice() is called or until the device is disconnected. It is therefore important for applications to clear the request when a call ends". If the device is unavailable the call "will be rejected and the method will return false". With competing apps "the priority is given to the application currently controlling the audio mode (see setMode)": so set `MODE_IN_COMMUNICATION` first. It replaces `startBluetoothSco`, `stopBluetoothSco`, `setSpeakerphoneOn`.
- `getAvailableCommunicationDevices()`, `getCommunicationDevice()`, `clearCommunicationDevice()`, `addOnCommunicationDeviceChangedListener(Executor, listener)` are all API 31 **[doc]** (the page lists them together; per-method API level read only for `setCommunicationDevice`).
- Legacy path for API 29-30: `startBluetoothSco()` / `stopBluetoothSco()` with `MODIFY_AUDIO_SETTINGS` (normal permission); "SCO connection establishment can take several seconds", so wait for the sticky `ACTION_SCO_AUDIO_STATE_UPDATED` to reach `SCO_AUDIO_STATE_CONNECTED` **[doc]**. Wired and USB headsets need no call: they win by default once `MODE_IN_COMMUNICATION` is on. `setSpeakerphoneOn(false)` for API 29-30 earpiece routing. **[ours]**
- Deprecations **[doc]**: `startBluetoothSco`, `stopBluetoothSco`, `isBluetoothScoOn`, `setSpeakerphoneOn`, `isSpeakerphoneOn` are deprecated in **API 34** (so deprecated, not removed, on 34 to 37: the legacy code stays behind `Build.VERSION.SDK_INT < 31`, with a suppress). `setBluetoothScoOn` and `isBluetoothScoAvailableOffCall` deprecated in **API 37**; the SCO broadcast actions and extras (`ACTION_SCO_AUDIO_STATE_UPDATED`, ...) deprecated in API 37 in favour of `addOnCommunicationDeviceChangedListener`. The API 37 notes appear in the live reference; compileSdk 37 therefore warns on the legacy-path calls: contain them in one `LegacyScoRoute` class with a file-level suppress.
- `BLUETOOTH_CONNECT` (API 31, dangerous, runtime) "Required to be able to connect to paired Bluetooth devices" **[doc]**. Targeting 12+ it replaces the legacy BLUETOOTH/BLUETOOTH_ADMIN (declare those with `maxSdkVersion="30"`) **[doc]** (bt-permissions). For our audio use: listing Bluetooth devices through `AudioManager.getDevices` works without it, but selecting a Bluetooth device as communication device (and reading its name) is treated as using the Bluetooth stack: ask for `BLUETOOTH_CONNECT` on API 31+ before `AudioRoute.start`. **[unverified: exact enforcement point for setCommunicationDevice]** The PermissionService owns the prompt; the native module should report `ERR_AUDIO_PERMISSION` rather than ask itself.
- A bonus of `BLUETOOTH_CONNECT` being granted: it also satisfies the `connectedDevice` FGS prerequisite (section 1).
- Cues: `AudioTrack`/`SoundPool` with `AudioAttributes.USAGE_VOICE_COMMUNICATION` follow the communication device. Never call `requestAudioFocus` for our own streams (the rider's music and navigation must keep playing); on Android 17 a background audio focus request fails with `AUDIOFOCUS_REQUEST_FAILED` anyway (section 7). **[ours]**

## 4. Wi-Fi Direct with stored credentials (M2)

Sources: https://developer.android.com/reference/android/net/wifi/p2p/WifiP2pConfig.Builder, https://developer.android.com/reference/android/net/wifi/p2p/WifiP2pManager, https://developer.android.com/reference/android/Manifest.permission

- `WifiP2pConfig.Builder` and `WifiP2pManager.createGroup(Channel, WifiP2pConfig, ActionListener)` are **API 29** **[doc]**. The builder "can be constructed for two use-cases: SSID + Passphrase are known: use setNetworkName and setPassphrase; SSID or Passphrase is unknown, in such a case the MAC address must be known and specified using setDeviceAddress". Both of the first kind's setters "Must be called".
- Rules **[doc]**: the network name "shall begin with DIRECT-xy" where x and y are upper case letters, lower case letters or digits, anything allowed for an SSID may follow (matches `config/identity.json` `wifiDirectNamePrefix: "DIRECT-pn-"`: `DIRECT-pn-` plus a pair-derived suffix). The passphrase is ASCII, length 8 to 63 in legacy PCC mode (`PCC_MODE_CONNECTION_TYPE_LEGACY_ONLY` / `LEGACY_OR_R2`), under 128 only with `R2_ONLY` (API 36 additions: `setPccModeConnectionType`, `setPairingBootstrappingConfig`); `setGroupOperatingBand`/`setGroupOperatingFrequency` exist since 29, `enablePersistentMode` since 29.
- Host: `createGroup(channel, config, listener)` makes this phone the group owner ("essentially creates an access point that can accept connections from legacy clients as well as other p2p devices"); then `requestGroupInfo` for the group details (owner address, interface name such as `p2p-wlan0-0`). Guest: `connect(channel, config, listener)` with the same name + passphrase; joining does not need a prior discovery when SSID and passphrase are known **[doc: use-case text]**; in practice a scan may still be needed on some chipsets **[unverified]**. Both sides afterwards see an interface `p2p-*` which `InterfaceClassifier` maps to `wifi-direct`, and `AdvertiseAddressSelector` prefers.
- Permissions per API level **[doc]** (identical sentence on createGroup / connect / requestGroupInfo): "If targeting TIRAMISU (33) or later, the application must have NEARBY_WIFI_DEVICES with android:usesPermissionFlags="neverForLocation". If the application does not declare neverForLocation, then it must also have ACCESS_FINE_LOCATION. If targeting an earlier release than TIRAMISU, the application must have ACCESS_FINE_LOCATION." `NEARBY_WIFI_DEVICES`: API 33, dangerous, runtime ("Required to be able to advertise and connect to nearby devices via Wi-Fi"). Manifest for M2:

```xml
<uses-permission android:name="android.permission.NEARBY_WIFI_DEVICES" android:usesPermissionFlags="neverForLocation" />
<uses-permission android:name="android.permission.ACCESS_FINE_LOCATION" android:maxSdkVersion="32" />
<uses-permission android:name="android.permission.CHANGE_WIFI_STATE" />
<uses-permission android:name="android.permission.ACCESS_WIFI_STATE" />
```

So: API 29-32 prompts for location (a user-visible oddity to explain in onboarding), API 33+ prompts for "Nearby devices" only. Location services may additionally have to be switched on for P2P discovery on API <= 32 **[unverified]**. Note the runtime group for `NEARBY_WIFI_DEVICES` is the same NEARBY_DEVICES group as `BLUETOOTH_CONNECT`, so one prompt can cover both on API 33+ **[ours, from the Android 17 page's statement that ACCESS_LOCAL_NETWORK is in the existing NEARBY_DEVICES group; membership of the older permissions not re-read]**.

- Brief risk 1 (WebRTC ignoring the `p2p-*` interface) is the media agent's; the facts needed from here are `LinkEndpoint.interfaceName` and `listInterfaces()` (both implemented in the M0 skeleton).

## 5. Behaviour on API 37 (Android 17), relevant if targetSdk is raised

Sources: https://developer.android.com/about/versions/17/behavior-changes-17, https://developer.android.com/about/versions/17/changes/bg-audio, https://developer.android.com/privacy-and-security/local-network-permission, https://developer.android.com/develop/connectivity/wifi/use-nsd, https://developer.android.com/reference/android/Manifest.permission

Targeting 37 is a deliberate later step (D-010). What would change:

1. **Local network permission** **[doc]**. `ACCESS_LOCAL_NETWORK` (API 37, dangerous, in the NEARBY_DEVICES group, "Required to be able to advertise and connect to local network devices"). For apps targeting 37 it gates, at the network-stack level and for every API: outgoing and incoming TCP connections to/from local addresses, UDP unicast/multicast/broadcast send and receive, `.local` name resolution, and `NsdManager` ("Use of framework-level classes that access the local network, for example, NsdManager"). A local network "uses a broadcast-capable interface such as Wi-Fi or Ethernet, but excludes cellular or VPN". That is our entire LAN transport and the Wi-Fi Direct group traffic: with targetSdk 37 the app must declare and request `ACCESS_LOCAL_NETWORK` before `LinkTransport.open`, otherwise connect, accept and mDNS fail. NsdManager offers a picker-based alternative (`DiscoveryRequest.FLAG_SHOW_PICKER`, a per-service grant that persists) which does not fit a hands-free flow; the app will use the permission. The prompt shares the NEARBY_DEVICES group, so a user who already granted Nearby devices is not asked again **[doc]**. Whether a Wi-Fi Direct group's p2p interface counts as "local network" is not stated on the pages read. **[unverified, test on an Android 17 device]**. On Android 16 the permission was opt-in (the page calls the prior opt-in "deprecated") **[doc]**. Our `PermissionService` needs a new kind and the TS link wrapper a `permission` LinkError path; the native module already declares `ERR_LINK_PERMISSION`.
2. **Background audio hardening** **[doc]**. All apps on Android 17 that play audio, request audio focus or change volume in the background "must have a visible activity or must be running a foreground service that is not of type SHORT_SERVICE" (any target). Apps targeting 37 additionally need the foreground service to have while-in-use capability, which a service gets when "started in response to a user-initiated operation or while the app is visible" (our user-tap start qualifies; a service restarted by the system or started from BOOT_COMPLETED does not). Failures are silent: playback is silenced, `requestAudioFocus` returns `AUDIOFOCUS_REQUEST_FAILED`, volume calls are ignored. Check with `adb shell cmd audio set-enable-hardening <enable|disable|throw>` and logcat lines prefixed `AudioHardening` (`level: full` = FGS without WIU, `level: partial` = no FGS) **[doc]**. Our cues (AudioTrack, voice-communication usage) and WebRTC playout must come from the running ride service: do not play a cue from a context when no ride service exists. The capture/mic side is already while-in-use gated since Android 14.
3. **Audio API deprecations** (compile-time) **[doc]**: `setBluetoothScoOn`, `isBluetoothScoAvailableOffCall`, the SCO broadcast actions (section 3). compileSdk 37 already shows these.
4. Other target-37 changes on the page (MessageQueue lock-free, static final fields unmodifiable via reflection or JNI, safer native DCL: `System.load` files must be read-only, large-screen orientation opt-out removed, certificate transparency default on, ECH for TLS, RFCOMM `read()` returns -1) have no direct effect on our code. The unmodifiable static finals and native-library read-only rule are worth a smoke test against libwebrtc and Hermes on an Android 17 device. **[ours]**
5. No new foreground service type or timeout for microphone/connectedDevice appears on the Android 17 behaviour page. **[doc, negative result]**

## 6. What the M0 skeleton already contains, and what M1 must add

- Implemented now (real platform calls, trivially safe): `IntercomLink.listInterfaces`, `isWifiConnected` (`ACCESS_NETWORK_STATE`, normal permission, declared in the module manifest), `IntercomAudioRoute.getState` (read-only device snapshot + selection policy, no mode change), `IntercomRideService.getBattery` and `isRunning`.
- M1 additions to the module manifest: the service and permissions of section 1, `CHANGE_WIFI_MULTICAST_STATE`, `MODIFY_AUDIO_SETTINGS`, `BLUETOOTH_CONNECT`, `WAKE_LOCK`, `ACCESS_WIFI_STATE` plus `BLUETOOTH` (maxSdkVersion 30) and `BLUETOOTH_ADMIN` only if the legacy SCO path needs them **[unverified; the SCO calls document only MODIFY_AUDIO_SETTINGS]**.
- Decisions to take with the lead before M1: where `POST_NOTIFICATIONS` and `BLUETOOTH_CONNECT` are requested (PermissionService, frozen) and whether the Link wrapper should refuse `open` when the local-network permission is missing once targetSdk is 37.
